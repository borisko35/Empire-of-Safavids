# Empire of Safavids — Развёртывание на VPS (Docker + HTTPS)

## 📋 Что нужно подготовить заранее

| Шаг | Что сделать | Где |
|-----|-------------|-----|
| 1 | Купить домен (например `sefevids.online`) | reg.ru / namecheap / cloudflare |
| 2 | Создать A-запись домена → IP вашего VPS | панель домена |
| 3 | Убедиться, что на VPS открыты порты **80** и **443** | панель провайдера (Oracle / Timeweb / Selectel). Для Oracle — ещё и `iptables` внутри машины, см. «Бесплатный хостинг» |

> Без домена Let's Encrypt не выпустит сертификат — игра будет работать только по HTTP (не рекомендуется).

## 🖥 Шаг 1: Подключитесь к VPS

```powershell
# Из PowerShell (Windows)
ssh <пользователь>@<ip-машины>
# пароль — ваш; в репозиторий не вносится
```

Пользователь зависит от хоста: `root` у Vultr и Timeweb, `ubuntu` у Oracle.

Или через **WinSCP**: хост `<ip-машины>`, пользователь `<пользователь>`, пароль — ваш (хранится вне репозитория, например в менеджере паролей).

## 🔑 Шаг 4: Настройте переменные окружения

```bash
cd ~/deploy
cp .env.example .env
nano .env
```

Заполните:

```env
DOMAIN=ваш-домен.ru          # ← ваша A-запись уже должна смотреть сюда

# Пароль PostgreSQL — сгенерируйте случайный:
POSTGRES_PASSWORD=XXXXXXXXXXXXXXXX

# Секрет JWT — сгенерируйте случайный:
JWT_SECRET=YYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYY

# Остальное можно не трогать — возьмёт значения по умолчанию
```

Сгенерировать пароли:
```bash
openssl rand -hex 16   # для POSTGRES_PASSWORD
openssl rand -hex 32   # для JWT_SECRET
```

Сохраните: **Ctrl+O → Enter → Ctrl+X**

## 🚀 Шаг 5: Запустите игру

```bash
cd ~/deploy
docker compose -f docker-compose.prod.yml --env-file .env up -d --build
```

Первый запуск может занять **5–10 минут** (скачивание образов + сборка).  
Следите за прогрессом:
```bash
docker compose -f docker-compose.prod.yml logs -f
```

Как только увидите `Empire of Safavids Server running on port 3000` — всё готово.

## 🔄 Обновление после изменений в коде

**С 10 октября 2026 выкатка идёт на AWS**, а не на домашний ПК: игра живёт на
`t3.micro` в Франкфурте, и домашний компьютер больше не обслуживает сайт.

### Сайт живёт здесь

| что | значение |
|---|---|
| адрес | **https://game.eos-gameonline.com/** |
| проверка | `https://game.eos-gameonline.com/health` |
| сервер | `18.197.33.141`, `t3.micro`, Ubuntu 24.04.4 |
| ключ | `~/.ssh/eos-key.pem` |

Домен лежит в `deploy/.env` на сервере и в `deploy/.env.example` стоит как
заглушка `game.example.com`. **Домен не выдумывается**: он читается из
`.env`. Первая проверка после выкатки била по придуманному имени и почти
отрапортовала, что сайт лежит, — а он отвечал 200.

### Как убедиться, что на прод уехал НОВЫЙ код

`RESULT: PASS` означает, что выкатка прошла, но не означает, что в образ
попал нужный код. Маркеры проверяются прямо в бандле клиента:

```bash
# маркеры новых зданий в сборке: customs, weaver, shrine
for m in customs weaver shrine; do
  printf "  %s: " "$m"
  docker exec empire-of-safavids-client-1 \
    sh -c "grep -ro '\$m' /usr/share/nginx/html/game 2>/dev/null | wc -l"
done
```

Кириллические комментарии из исходников в бандл не попадают — сборщик их
вырезает. Искать надо идентификаторы, а не русские заголовки комментариев.

### Туннель моргает — и это нормально

6 октября 2026 в 22:01:40 `cloudflared` отдал
`datagram manager error: timeout: no recent network activity` и через две
секунды переподключился (`fra18`, QUIC). Сайт в этот момент отвечал 200.
На `t3.micro` всего 911 МБ памяти, и QUIC-туннель на ней чувствителен. Если
моргания станут частыми — смотреть своп и UDP-буферы, их настраивает фаза 0.5
в `tools/bootstrap-machine.sh`.

Порядок такой:

1. На домашнем ПК — правите код и **отправляете** его:

   ```
   git push origin main
   ```

2. На сервере — забираете код **и выкатываете**:

   ```bash
   ssh -i ~/.ssh/eos-key.pem ubuntu@18.197.33.141
   cd ~/Empire-of-Safavids
   git pull --ff-only origin main
   bash tools/deploy.sh
   ```

Одной строкой с домашнего ПК:

```powershell
& "C:\Program Files\Git\bin\bash.exe" -lc "ssh -i ~/.ssh/eos-key.pem ubuntu@18.197.33.141 'cd ~/Empire-of-Safavids && git pull --ff-only origin main && bash tools/deploy.sh'"
```

**`git pull` до выкатки обязателен, и это не совет, а требование скрипта.**
`deploy.sh` **не выполняет `git pull` намеренно** и сверяет локальный коммит с
запушенным: если они разошлись, выкатка останавливается с «lokальный коммит не
равен запушенному». То есть забытый `pull` даёт не тихую выкатку старого кода,
а явную остановку. Это сделано после инцидента 30 сентября, когда на прод уехал
старый код, а выкатка отрапортовала успех.

Если на сервере лежит незакоммиченный или незакоммиченный-но-неотслеживаемый
файл, `git pull` об него споткнётся:

```bash
git status --porcelain | grep '^??'
```

**Если вы всё-таки держите стек на домашнем ПК**, выкатка запускается там же
полным путём к Git Bash:

```powershell
& "C:\Program Files\Git\bin\bash.exe" tools/deploy.sh
```

Просто `bash tools/deploy.sh` в PowerShell **не работает**: команда `bash` там
указывает на `C:\Windows\system32\bash.exe`, это заглушка WSL, а WSL не
установлен. Вызов падает с `execvpe(/bin/bash) failed` — и выглядит как
«сломалась выкатка», хотя сломана оболочка. В cmd и в самом Git Bash короткая
форма работает.

Скрипт делает всё сам и **останавливается на первом непроверенном шаге**:
предварительная проверка, затем сверка «коммит
изменился», затем пересборка, затем проверка, что сервер отвечает.

**Почему не три команды вручную.** Именно так выкатка и выглядела, и 30
сентября это стоило трёх коммитов, которые на прод не попали, хотя выкатка
отрапортовала об успехе:

```
git pull --ff-only origin main 2>&1 | tail -3 && docker compose ... up
                                               ^^^^^^^^^ код берётся у `tail`
```

`git pull` **упал с кодом 1** — на сервере лежал незакоммиченный
`tools/build-trailer.sh`, а git не перезаписывает неотслеживаемые файлы.
Код возврата пайпа взялся у `tail`, он всегда ноль, `&&` исполнился, и
контейнеры пересобрались на старом коде. В выводе стояло
`Updating deef120..ec30537` — а эта строка git печатает **до** отказа.

**Что делает скрипт и почему каждая проверка нужна**

1. `tools/deploy-preflight.sh` — ничего не меняет, но останавливает выкатку,
   если нет `deploy/.env`, если `git` смотрит не в папку игры или если `docker`
   не отвечает (проверяется `docker info`, а не `docker --version`: версия
   читает файл и отвечает даже при недоступном сокете).
2. **Сверяется локальный коммит с запушенным.** Если разошлись — остановка.
   `git pull` тут **не выполняется**: он и не нужен (код уже забран на сервере),
   и спотыкается о незакоммиченные файлы. Расхождение означает забытый `pull`.
3. Незакоммиченные правки в `client`, `server`, `shared` запрещены: на образ
   уедет ровно то, чего нет в репозитории. Правки в `ROADMAP` или `deploy/`
   на образ не влияют и выкатку не блокируют.
4. `docker compose up -d --force-recreate --build server client`. Заодно
   создаётся контейнер туннеля, **если его на машине нет**: `cloudflared` не
   входит ни в чьи `depends_on`, и `up` с явными именами сервисов его не
   поднимает. Пересоздаётся он только когда не работает — у образа тег
   `latest`, пересобирать нечего, а пересоздание роняет сайт на минуту.
5. Сервер опрашивается до 90 секунд: контейнеру нужно время на миграции,
   и без ожидания проверка успела бы ответить на ещё старом процессе.
6. Сверяются ID образов до и после сборки. Если образ не изменился — это **не
   ошибка**: слои те же, код не менялся, пересобирать было нечего.
7. Читаются **файлы** моделей с диска образа, а не по HTTP. По HTTP проверка
   не может упасть: nginx отдаёт `index.html` на любой несуществующий путь, и
   все модели выглядят «на месте» при полном их отсутствии.
8. Туннель должен быть не просто `running`, а **подключённым**: сверяется
   запись в его журнале о регистрации соединения с Cloudflare, и их число
   попадает в отчёт.

Если выкатка упала на шаге 2, смотрите лог: обычно мешает незакоммиченный
файл на сервере. Список таких:

```bash
git status --porcelain | grep '^??'
```

**Почему проверка идёт первой.** Пересборка — это перезапуск сервера
игры. Если файл `deploy/.env` исчез, сервер не поднимется, и сайт
ляжет с 502 — при этом в логах пересборки ошибок не будет, ведь ошибка
возникает позже, при чтении настроек. Именно так было 27 сентября: файл
секретов пропал, логи были зелёные, а сайт лежал, пока искали причину.

Проверка также сверяет, куда наведён `git`. Если репозиторий указывает
на другую папку, `git pull` и `git reset` бьют не по игре, и это надо
знать ДО команды, а не после.

Миграции БД применятся автоматически перед стартом сервера. Если
миграция упала, сервер не поднимется — это сделано намеренно: лучше не
подняться, чем подняться со старой схемой базы и падать при первом
обращении игрока.

## 🆓 Бесплатный хостинг

### Коротко: почему сайт лежит, когда выключен ПК

Сейчас игра крутится на домашней машине, наружу выходит туннель Cloudflare.
Пока компьютер включён — сайт работает. Выключили — сайт лёг. Это не ошибка
конфигурации, а прямое следствие того, что источник находится дома.

**Единственный бесплатный вариант, который тянет весь стек с постоянной базой —
Oracle Cloud Always Free:** 4 ядра ARM и 24 ГБ памяти, навсегда бесплатно.
Проверено: `node:20-alpine`, `nginx:1.27-alpine`, `postgres:16-alpine`,
`redis:7-alpine`, `caddy:2-alpine` и `cloudflare/cloudflared` публикуют
`linux/arm64`, то есть **пересобирать образы под ARM не нужно**.

Остальные бесплатные тарифы не подходят: у них либо нет постоянного диска
(данные Postgres пропадут при перезапуске), либо машина засыпает через 15 минут,
либо карта всё равно нужна, а после пробного периода счёт выставляют.

**Что нужно от вас и только от вас:** создать аккаунт Oracle Cloud. Это
регистрация с картой (списывают доллар и сразу возвращают). Аккаунт прошлой
попытки деактивирован, так что нужен новый.

**Что сделано заранее, чтобы переезд не занял день:**

```bash
ssh ubuntu@<ip>
bash tools/bootstrap-machine.sh
```

Скрипт ставит Docker, клонирует репозиторий, проверяет секреты, зовёт
выкатку и проверяет результат. Он идемпотентен: повторный запуск ничего не
ломает, так что после любой ошибки его можно пустить снова.

**Ключевое решение, принятое заранее: мы НЕ открываем порты и не даём машине
свой IP.** Идём тем же туннелем Cloudflare. Тогда отпадают сразу три ловушки,
на которые уходил день:

| ловушка | как решено |
|---|---|
| порт открыт в панели Oracle, но закрыт в `iptables` | порты не открываются вовсе |
| Caddy не получает сертификат | сертификат выпускает Cloudflare |
| нужно менять A-запись домена | адрес уже указывает на туннель, DNS не трогаем |

Если токена туннеля в `deploy/.env` нет, скрипт честно скажет об этом и
напечатает команды для варианта с прямыми портами.

VPS от Vultr отключён за долг. Код и вся сборка живут в git, поэтому
переезд — это новая машина плюс три вещи ниже. Обе схемы используют один и
тот же `docker-compose.prod.yml`: править код не нужно.

### Путь 1. AWS Free Tier — выбран 10 октября 2026

Oracle отпадает по карте: Oracle требует **дебетовую карту, не требующую ввода
ПИН-кода**, а у владельца только виртуальная, и проверку она не проходит. AWS
виртуальную принимает — проверено, аккаунт создан, машина запущена.

**Сколько это стоит и на сколько.** С 15 июля 2025 AWS поменял бесплатный тариф:
новому аккаунту дают **$100 кредитов** (и до $100 за задания) и **6 месяцев**, не
12. Реальный расход нашего стека: машина и диск — $0, **публичный IPv4 — $3.60 в
месяц**, трафик игры — около $1. Итого **~$4.60 в месяц из кредитов**. Списаний
не будет, пока владелец сам не переключит аккаунт на платный план. Через 6
месяцев бесплатный план закроется сам — это решение принимается тогда, у нас
будет полгода на спокойный разбор.

| Шаг | Что делать | Где |
|-----|------------|-----|
| 1 | Регистрация (карта, списывают $1 и возвращают) | portal.aws.amazon.com/billing/signup |
| 2 | Бюджет-предохранитель на $5 с порогом 80% | Billing → Budgets |
| 3 | Создать EC2: `t3.micro`, Ubuntu 24.04, 30 ГБ gp3, ключ `eos-key` | EC2 → Instances → Launch instance |
| 4 | Взять публичный IPv4 | на странице самой машины |

Поля, которые важны, и почему:

- **`t3.micro` с пометкой Free tier eligible.** 2 vCPU, 1 ГБ.
- **Диск 30 ГБ, `gp3`, а не стандартные 8 ГБ.** Замерено на этой машине: образы
  занимают 1.1 ГБ, во время сборки Docker раздувается ещё на ~2 ГБ, база 70 МБ,
  система ~4 ГБ. На 8 ГБ сборка упирается в конец диска и падает на середине.
  Расширить потом легко, уменьшить — нет, поэтому берём сразу с запасом.
- **В группе безопасности только SSH (22).** Ни 80, ни 443: наружу выходит
  туннель Cloudflare, cloudflared соединяется сам. Источник SSH — «Моё IP» или
  «Любой»; пароля на машине нет, вход только по ключу.
- **Гибернацию выключить.** Поле «Durdur — Hızında Beklet davranışı» со значением
  `Etkinleştir` приводит к отказу `For hibernation, the root device volume must
  be encrypted`: AWS умеет быстрое сохранение состояния только на зашифрованном
  диске, а машина у нас обычная.
- **Ключ создаётся кнопкой «Create new key pair», а не вставкой.** Поля для
  вставки публичного ключа в мастере AWS нет — он выдаёт RSA 2048 и сам
  скачивает `.pem`. Отпечаток:
  `SHA256:9qQl3ekIkYakIjw+KWiNAB800IhDctod7GbBDXothdU`.

**Про группу `docker` — об этом стоит знать.** На новой машине переезд
останавливается с `permission denied ... /var/run/docker.sock`: установщик
Docker добавляет пользователя в группу `docker`, но права группы действуют
только в **новой** сессии, а переезд запускают по уже открытой. Скрипт
`tools/bootstrap-machine.sh` это видит и перезапускает себя через `sg docker`,
поэтому одной командой всё и обходится. Но **руками** `docker` на этой машине
заработает только после перезахода по ssh — это не поломка, а особенность Linux.

### Путь 2. Oracle Cloud Always Free

**Недоступен: нужна физическая дебетовая карта.** Требование Oracle — карта с
логотипом Visa/Mastercard/Discover/Amex, не требующая ввода ПИН-кода, плюс
включённые интернет-оплаты, международные операции и 3-D Secure. Виртуальная
карта проверку не проходит, и текст об этом есть на самой странице регистрации.
Остальное ниже верно и применимо, если карта появится.

Бесплатно навсегда: до 4 ядер ARM и 24 ГБ памяти на аккаунт. Нашей связке
(postgres + redis + игра) хватает с запасом.

**Мы идём через туннель Cloudflare, и это меняет всё.** Ниже — что из-за этого
убрано из инструкции: не нужны открытые порты, не нужна правка `iptables`, не
нужна смена DNS и не нужен сертификат. Подробности — в «Бесплатный хостинг»
выше; здесь только шаги машины.

| Шаг | Что делать | Где |
|-----|------------|-----|
| 1 | Регистрация с картой (списывают доллар и сразу возвращают) | cloud.oracle.com/free |
| 2 | Создать VM: shape `VM.Standard.A1.Flex`, **1 OCPU и 6 ГБ памяти**, диск 50 ГБ | Compute → Instances → Create instance |
| 3 | Вставить SSH-ключ машины (см. ниже) | там же, поле «Add SSH keys» |
| 4 | Взять IP машины | на странице самой VM |

Ключ для шага 3 — вставьте его поле «Paste public keys» целиком, одной строкой:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIKtIuyofHzPY5II73QS0LVMp/34lgnJo2DfNu7c7XIOp user@MASA-19
```

Отпечаток: `SHA256:a7gLN8h4NnpIdAajT3eyFU3nwUwO9oaLbu5FtnTPlUI`. Приватная часть
остаётся на этой машине, и переезд выполняется с неё — вводить пароль вручную
не придётся.

**Берите МИНИМУМ, а не 2 ядра и 12 ГБ.** Бесплатных ARM-машин не хватает, и
чем больше просишь, тем дольше `Out of host capacity`. 1 OCPU и 6 ГБ нашей
связке хватает с трёхкратным запасом по памяти, а расширить потом можно за
минуту. Просить максимум — значит ждать часы без машины.

**Порты 80 и 443 открывать НЕ нужно.** Через туннель Cloudflare наружу выходит
cloudflared, а он соединяется сам. Образы Oracle держат `REJECT` для всего,
что не разрешено явно, и без туннеля именно на них уходил день: порт открыт
в панели, а в системе закрыт. С туннелем вопрос не возникает.

**A-запись домена менять НЕ нужно.** Адрес уже указывает на туннель, а он один
и тот же. Переезд не трогает DNS.

#### Подводные камни, на которых уходит день времени

- **Нет свободных машин.** Самая частая ошибка — `Out of host capacity`. Это не
  поломка: бесплатные ARM-машины разбирают быстрее, чем появляются, особенно в
  популярных регионах. Регион выбирается один раз и потом не меняется, поэтому
  при нехватке берите другую региону и заводите машину заново, а не жмите
  «Create» снова по кругу.
- **Пользователь — `ubuntu`, а не `root`.** Вход: `ssh ubuntu@<ip>`.
- **Архитектура ARM.** Проверено по манифестам Docker Hub: `node:20-alpine`,
  `nginx:1.27-alpine`, `postgres:16-alpine`, `redis:7-alpine`, `caddy:2-alpine`
  и `cloudflare/cloudflared` публикуют `linux/arm64` наряду с `amd64`. То есть
  пересобирать образы под ARM не нужно, а вот apt-пакеты, если их придётся
  доустанавливать, искать надо `arm64`-варианты.
- **SSH-ключ вставляется при создании VM, а не после.** В консоли есть поле
  «Add SSH keys»; вставить туда публичную часть. Приватная остаётся на этой
  машине, и переезд делается с неё.

### Путь 3. Домашняя машина + туннель Cloudflare

Ни карты, ни белого IP, ни оплаты. Домен остаётся прежним, но его DNS надо
перенести на бесплатный тариф Cloudflare (это бесплатно и занимает минуты
после смены NS у регистратора).

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.tunnel.yml \
  --env-file .env up -d --build
```

Дополнение `docker-compose.tunnel.yml` делает две вещи:

- **Выключает Caddy.** Сертификат выпускает и терминирует Cloudflare, а
  образа к нашему адресу от сервера не приходит. Caddy остаётся в
  `docker-compose.prod.yml` нетронутым — выключается он профилем, который
  никто не включает.
- **Добавляет `cloudflared`** внутрь той же сети compose. Он ходит на
  `client:80` по имени сервиса, поэтому порты на машине не публикуются и
  в брандмауэре открывать нечего.

Токен кладётся в `deploy/.env`:

```
CLOUDFLARE_TUNNEL_TOKEN=<длинная строка из панели Cloudflare>
```

Без неё compose не стартует вовсе, а не стартует вслепую.

**Что нужно на машине.** Docker (Docker Desktop с WSL2 на Windows: после
установки нужна перезагрузка). Стек умещается в 4 ГБ памяти, но для
комфортной игры лучше 8 ГБ.

**Честно о минусах.** Машина должна быть включена всегда: выключили —
игра лежит, и починить можно только вручную. Скорость зависит от
домашнего интернета. Это запасной путь, а не постоянный хостинг, но он
работает сегодня и ничего не стоит.

### Проверка после переезда

```bash
curl -s http://localhost/health          # → {"status":"ok",...}
docker compose -f docker-compose.prod.yml ps   # все контейнеры healthy
```

Снаружи: `https://game.eos-gameonline.com/game/`. Если локально отвечает, а
снаружи нет — см. разбор ниже.

**Что означает «локально отвечает, а снаружи нет».** На туннельном пути ни
порты, ни DNS в этом не участвуют: наружу выходит cloudflared, а он сам
соединяется с Cloudflare. Значит, если локально стек зелёный, а снаружи нет —
виноват туннель, и проверять надо его:

```bash
docker compose -f deploy/docker-compose.prod.yml \
  -f deploy/docker-compose.tunnel.yml ps cloudflared   # должен быть running
docker compose -f deploy/docker-compose.prod.yml \
  -f deploy/docker-compose.tunnel.yml logs --tail=20 cloudflared
```

Порты и DNS относятся только к пути, где Caddy слушает 80 и 443 напрямую. На
туннельном пути (AWS, домашняя машина) ни порты, ни DNS в этом не участвуют.

## 🛠 Полезные команды

```bash
# Перезапуск
docker compose -f docker-compose.prod.yml restart

# Логи
docker compose -f docker-compose.prod.yml logs -f server

# Остановить всё
docker compose -f docker-compose.prod.yml down

# Удалить volumes (сброс БД!)
docker compose -f docker-compose.prod.yml down -v
```

## 🔧 Если что-то не работает

| Проблема | Решение |
|----------|---------|
| `docker: command not found` | `curl -fsSL https://get.docker.com \| sh` |
| Сервер не запускается | `docker compose -f docker-compose.prod.yml logs server` |
| Ошибка `POSTGRES_PASSWORD` | Проверьте `.env` — пароль должен быть задан |
| CORS-ошибка в браузере | Убедитесь, что `DOMAIN` в `.env` совпадает с адресом в браузере |
| 502 Bad Gateway | `docker compose -f docker-compose.prod.yml ps` — проверьте, что все контейнеры `healthy` |
| Let's Encrypt не выпускает сертификат | Убедитесь, что порт 80 открыт снаружи и DNS указывает на этот VPS |
